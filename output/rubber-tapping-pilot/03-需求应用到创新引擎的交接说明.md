# 需求应用到创新引擎：本次实验的交接说明

需求应用输出应是可追溯的任务定义，而非一句“帮我创新”。本次以需求包.json作为原型，输出15项带ID的需求，经过Host适配为ProblemBrief，再调用方法引擎与案例MCP。尚未开发一个线上需求库或新的需求MCP服务。

## 最小交接字段

- request_id、revision、输入来源、确认状态、适用对象和任务边界。
- 每项需求的ID、相关主体、需要达到的结果、硬软属性、验收口径、来源及未知；数值未知保持空值。
- 来源记录的版本、定位与实际核读范围；行业文献支持问题存在，不代表客户批准该需求。
- 批准记录及有权确认的人。当前approved=false，不能由模型改成true。

当前hard_proposal字段是研究者建议；进入ProblemBrief时hard=true仍只是proposed要求。hard=null表示尚未确认硬软属性，不能转换成false。需求澄清之后变更版本，旧运行和假设保留。

## 正常执行

1. 检查对象、边界与缺口。缺少关键信息时形成澄清问题，或明确限定为研究模式。
2. 方法调度返回理由、前置输入、允许结论层级和专业资源缺口。既可采用规则与参考DAG，也可调用可选语义组件，两者记录分开。
3. 案例库按功能/机理查找，读取来源，再判断适用条件与差异。案例指标不能成为客户参数。
4. Host Agent依据方法组织功能、候选、比较和验证计划；各产物带任务版本、ID和证据引用，逐步检查并持久保存。
5. 方案报告回到每项需求，输出候选、未知、反例和下一步补证。证据不足时不推荐唯一方案。
6. 客户反馈与真实试验形成新需求/运行版本；回流记录不得改写源案例事实。

## 本次实际情况

可选语义模型调用遭遇429及180秒超时，未完成自动生成。Host Agent继续阅读真实方法与案例资料并组织六份产物，实际通过方法MCP校验、提交和重启读取。不存在用规则结果伪装语义模型成功的替代。

需求包摘要与指纹连接到task.json；engine-report.json保存运行与检查；Agent推理产物.json保存六份内容。case-retrieval-audit.json保存来源定位和指纹，原件正文与数据库在private目录，不包含在交付ZIP。
