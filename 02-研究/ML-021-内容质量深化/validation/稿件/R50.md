# 服务蓝图：把客户看到的动作连到后台责任与异常恢复

蓝图不是顺畅旅程的海报。它从用户行动出发，显示可见接触、后台工作、支撑流程和证据对象之间的依赖，帮助团队发现“每个部门看似完成，用户却等不到结果”的断点。NN/G原文章说明这些层与交互/可见分界；本例为平台构造的服务改版，不冒称现场调研。[NN/G，Service Blueprints: Definition](https://www.nngroup.com/articles/service-blueprints-definition/)

先确定一段服务边界、目标角色与情境，分清观察现状和未来设想。逐事件写用户想做什么、前台承诺了什么、后台需要谁完成、支撑系统提供什么、什么证据使下一步可继续。前台/后台按对用户可见划分，不按职级；同一人可跨层。等待起止必须清楚：等待接单与实际处理不能混成一个总时长。

完整构造例为某班次异常维护交接。步骤1操作者报异常，前台显示“已提交”；后台通知队列没有明确接收者。步骤2用户等待，构造事件记录t=0提交、t=12分钟有人查看、t=20分钟确认接单；其中20分钟是接单等待，不是修理工时。步骤3维护处理完成，但前台“已完成”同时被操作者理解为允许恢复。失败点是接单责任不明确和完成语义跨越恢复授权，而非简单“页面太慢”。

未来版蓝图给后台队列一个明确待任命责任角色，分开已提交/已接单/处理中/处理完待恢复核查；支撑系统保存接单人与未决项；超出约定接单窗口时升级协调，而不是自动关闭。恢复链要求维护范围记录、相关状态和授权分别有责任，不能由界面完成按钮替代。

在第二段**构造回放**中，t=0提交、t=3分钟接单、t=15分钟维护记录完成，仍显示恢复待核，t=18分钟补齐授权证据。教学判断是新蓝图消除了“无人负责接单”与“维护完成自动等恢复许可”的表示缺口；不能据这两次虚构事件统计真实等待下降率。实际窗口值必须由服务能力与风险后果定义，不直接采用本例3/18分钟。

产物从事件证据表转为多层蓝图，再转责任与恢复表、未来差异和观察计划。每个改动说明要改变哪个失败机制；若只是移动卡片而不改变接收、资源或信息，等待可能原样存在。真实改版后还需观察异常分支、跨班次、缺备件和无法联系人员的情况。

两种误用是把未来设想混画为现状，以及让前台承诺没有后台资源/责任接住。另一情境文档交付同样要区分“已提交生成”“文件可取”“权限已给”“接收者确认”，维护蓝图中的角色和证据不可照搬。

R09/R13补任务与人因，R45/R43讨论服务全寿命代价，R42确认具体改动的效果。引擎输出应是接触—后台—责任—证据—恢复的连贯设计，而非只列旅程步骤。

## 把责任落到蓝图表

下表完全为前述构造改版，角色均待实际任命。

|用户事件|可见接触|后台责任|支撑与证据|失败/恢复|
|---|---|---|---|---|
|报异常|已提交，不宣称已接单|接单协调角色|队列/时间与接收身份|无人接单则升级协调|
|等待处理|显示当前责任与未决|维护分派角色|工单与资源状态|资源不足保留未决，不自动结案|
|维护记录完成|处理完，恢复待核|维护执行角色|范围/状态记录|缺实际状态则回核查|
|请求恢复|显示恢复审查状态|恢复授权角色|实际状态与授权依据|不得用维护完成按钮代授权|
