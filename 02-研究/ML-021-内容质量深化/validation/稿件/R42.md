# 验证与确认：分别证明“符合已定义要求”与“满足实际用途”

同一设备可以按图纸制造正确，却无法在用户情境完成任务。验证检查产品是否满足规定要求，确认研究它在预期环境是否满足使用者期望。NASA系统工程手册5.3与5.4分别说明这两类活动，并关联配置、方法和证据；本文构造记录不替代项目要求基线。[NASA，Product Verification](https://www.nasa.gov/reference/5-3-product-verification/)；[NASA，Product Validation](https://www.nasa.gov/reference/5-4-product-validation/)

准备时先问被证明的声明是什么、谁批准、针对哪个配置/环境。把声明写成可以判定的对象/属性/条件/判据，选检查、分析、演示或测试等能支持的证据；方法名称不自动赋予证明能力。记录仪器/模型适用性、样本、原始资料、异常与判定责任。要求未确定时可以做研究计划，但不能填写“符合”结果。

完整构造例为文档交付工具CONFIG-D1。教学要求RQ1规定导出文件内版本标识应与指定源版本v3一致；预期用途U1是收件人在约定环境能打开并核对所需内容。验证记录V1输入源版本v3与导出文件，检查文件内部标识v3，判据一致，结果“RQ1在D1本文件满足”。确认记录VAL1在构造阅读环境E1尝试打开，因字体缺失无法显示关键表，判定用途未满足。V1不能覆盖VAL1；反过来，用户觉得好读也不证明版本标识满足要求。

修改CONFIG-D2采用嵌入字体与固定版式。构造重新检查标识仍v3，再在同一E1复看表格可见且能定位指定条目，教学决定保留D2作为该环境的符合/用途候选。全部记录均为人工构造，不是实际用户研究。若下一次改成环境E2或不同表格，需影响分析，不能拿D2/E1记录自动证明新组合。

偏差闭环要保留预期/实得、影响声明、临时措施、原因调查、修改、复测和未覆盖风险。问题可以“已修复”“需补证”“不适用”“变更要求待批准”，不能所有都归绿色通过。变更需问旧证据的输入、模型、配置或用途是否仍成立；仅文件名相同不够。构造例也展示为何验证/确认不是在流程末尾一次性做完。

两种误用是把学习原型反馈当产品验收，或把一个代理材料上的性能测试扩成真实树体/现场确认。对割胶问题，当前RQ候选仍不完整、未批准，阈值和环境未定，应先形成可验证声明与确认情境，再安排实际取证。R44用于减少不确定性，R42用于形成明确声明的证据；两者可以使用相同工具，但证明身份不同。

交付应含声明及版本、产品配置、方法/模型/仪器、环境/样本、原始记录、结果与异常、判定/责任及复用边界，向项目接受程序交接。完整报告不代表所有证据已收集，必须逐条显示支持到哪一层。
