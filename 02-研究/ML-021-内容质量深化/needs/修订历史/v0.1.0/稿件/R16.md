# 根因分析：让取证去区分解释，而不是把“为什么”问到一个人

本方法用于异常/事故/质量偏差后重建机制并形成行动。HSE原因说明及HSG245的收集、分析、控制和行动选段为依据。它是调查方法族，不等于固定五次为什么，也不能单凭一张鱼骨图证明因果。R40从预想失效向后果展开，R16则从已发生事件回查；系统交互问题还可交R51。

## 先稳住证据与调查范围

保存事件对象、配置、时间、载荷/环境及原记录，不让后来的顺畅解释覆盖当时材料。必要的现场处置与安全责任由实际人员承担，调查不能要求重演危险事故。对日志、照片、陈述逐项写它实际记录什么、缺什么和是否受事后变化影响。

时间线只说明已知先后，不能把空档补成因果。并行建立机械作用、信息/决策、组织支持和对象变化的候选解释。每个解释写“若成立还应该看到什么”“什么材料会削弱它”“反例是否同条件”。可行动性与因果已证分开。

## 沿既有偏移事件完成一次分析

以下全部构造：ER1为操作者事后认为夹紧；ER2为请求已发日志；ER3为滑移痕迹；ER4为绿灯只表示请求发出的规范；ER5为另一对象、无作业载荷的后查未滑移。

先形成证据能力表：ER2不证明实际夹紧，ER3不指向唯一原因，ER5不代表事件暴露。竞争解释H1保持作用不足、H2请求指示被当完成、H3对象状态变化均待查。把ER5直接写成“机械作用已排除”应拒绝，因为载荷/对象不匹配。

区分性取证表进一步具体化：H1需要事件条件下的实际接触/保持与载荷记录；H2需要当时可见界面及决策过程，而不只事后表达；H3需要对象/工况变更及可比记录。顺序按证据易失、风险及能否区分解释安排，不先默认培训是唯一措施。

为了教会有限决策，再加**纯构造文档偏差**：要求产物版本与请求相同，请求v2、导出清单明确v1，交付链无其他改写。可以确定版本选择/传递链存在不一致，先隔离错误产物并查选择记录；但仍不能仅凭它判断究竟是操作者选错还是软件映射错。已经能采取限制传播和补日志的行动，不必等唯一“根因”才纠正已知偏差。

## 行动和有效性怎样闭环

每项措施写作用机制、针对哪条解释、实施责任、完成证据、新风险和复查方式。“改灯含义”可能减少误解，但不修复实际夹力不足；两项可以并行研究，避免一项措施被写成全部根治。完成安装与控制有效也分开。

后续在可比任务暴露下记录异常与正常、条件及观察窗口。既有教学后续暴露0且事件0，事件率应为null；即使有正暴露，比率也只是描述，仍要核变化和混杂。不能以“没有投诉”或没有再运行来宣称100%改善。

两个失败反例：将最后动作归于操作者便终止分析，遗漏系统信息/组织条件；把无载荷试验无偏移当加载事故的反证。资料打不开也可能由生成、传输和阅读环境导致，现象相同不等一个原因。

交接包括事件/证据能力表、时间线、竞争解释、区分性取证计划、措施机制、实施与同类暴露复查。真实事故调查、现场因果和措施成效仍需实际证据；本文给的是足以开展调查而不预设答案的协议。
