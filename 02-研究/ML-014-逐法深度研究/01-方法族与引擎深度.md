# 方法族不同，深挖与调用方式也应不同

以下为平台研究编排建议，不修改现有A—G分类，不认定为原作者共同提出的统一分类。同一条方法可能跨多个层次。

| 方法族 | 代表内容 | 深度应体现在哪里 | 引擎应作什么 |
|---|---|---|---|
| 组织设计过程的框架 | 系统化工程设计、双钻、V模型、阶段门、集合式并行工程、WB总体体系 | 各阶段的判断、证据门槛、责任与回返，而非只画顺序箭头 | 编排子方法和决策门，不能当一次调用就完成的求解器 |
| 获取与解释需求证据 | 用户观察、JTBD、领先用户、Kano、人本设计、服务蓝图 | 采样情境、记录与解释分离、需求如何从证据产生、如何反证 | 给提问/研究协议，保存原话和假设，等待真实研究材料 |
| 表达问题与解空间 | 功能分析、FAST、形态学、C-K、DSM、公理化设计、FBS | 表达对象的语义、关系类型、约束与可检查的中间结构 | 先检查表示是否成立，再组合或比较；不把图形连线当物理证实 |
| 启发与知识迁移 | 仿生、设计启发式、TRIZ具体工具、功能导向检索、进化趋势 | 为什么可迁移、哪些条件不相同、排除和失败的理由 | 提供候选假设与证据检索，禁止把启发式当保证成功的规律 |
| 形式化工程分析 | 机构综合、材料选择、拓扑优化、DOE、稳健设计 | 变量、量纲、边界条件、模型适用性、求解器与可复算例 | 要求对应计算/仿真工具和真实参数；语言解释不能替代数值或几何求解 |
| 决策、风险与学习 | Pugh、多准则分析、FMEA、机械风险、STPA、V&V、LCA、VOI | 比较口径、硬要求、未知、研究信息价值和验证证据 | 不把未知判成通过，分开推荐、检查、专业审核与工程验证 |
| 专题和谱系性知识 | WB主辅功能/动态/智能/可视/质量评价/专家系统等 | 具体原典、版本、研究对象及内部方法，不把主题标题当独立算法 | 先确定具体对象和子方法；未有完整步骤时作为知识与研究指引调用 |

## 四种“看上去差不多”，实际不能混用的关系

**分解功能与选择机构**：功能表达的是要实现的作用；候选结构需要机制和行为依据。NASA设计章节将要求、逻辑分解和设计方案联系起来，并保留迭代和接口。我们据此要求引擎保存“功能为何必要”和“结构如何实现”的不同论证，不因读到某个成功案例就直接指定同形零件。[NASA系统设计4.3—4.4](https://www.nasa.gov/reference/4-0-system-design-processes/)

**概念筛选与工程验证**：筛选记录表达在现有信息下的相对判断；验证要有对要求的实际证据。反过来，即使若干性能要求通过，仍需要检查目标用户在预期使用环境中的需求是否满足。两种目标、证据和未覆盖项分开保存。[NASA产品验证5.3](https://www.nasa.gov/reference/5-3-product-verification/)，[产品确认5.4](https://www.nasa.gov/reference/5-4-product-validation/)

**研究问题很多与研究价值很高**：未知数量不能替代决策影响。应问哪种观测可能改变选择，以及获取信息的代价和时机。这是把VOI与原型/试验设计相接的理由，不是缺概率时编造数值排序。[NASA决策分析6.8](https://www.nasa.gov/reference/6-8-decision-analysis/)

**一套理论与一张可执行卡**：TRIZ、系统工程、WB综合设计等方法族覆盖多个工具、对象和判断。将整个体系压成五步可以帮助导航，却不代表已实现体系内全部推理。应先明确所调用的子方法、输入和预期产物，才能验收其执行。

## 对未来方法引擎的具体要求

1. 先识别任务阶段、对象、已有材料与关键未知，而非先挑一个熟悉方法。
2. 检查本法的最低输入：缺的是可以继续检索的材料，还是必须由客户/工程现场提供的条件？
3. 输出中保留证据、推测、教学假设与求解结果的身份，不用“模型有把握”替代依据。
4. 每个关键判断都能回答通过/否定/未知时分别往哪里走；缺少计算或专业能力时停止强结论。
5. 交接验证的是字段含义、版本与适用条件，不能只因为JSON有同名字段就判断兼容。
6. 检索内容库、执行契约、专业审核与真实工程验证独立发布。当前六项契约只是已建执行接口的范围，不代表六项已完成专家认证。
