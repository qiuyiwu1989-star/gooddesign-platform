# 深度如何进入产品创新引擎，而不变成更多表单

这是本平台的产品与调用设计建议，尚未实现为新的自动路由器。

方法库变深之后，前台仍应从用户的问题出发。专业结构留在引擎内部；用户只需要确认真正影响判断的内容，并能在需要时核对依据。

## 一次有价值的追问，应改变后续工作

例如用户说“割胶后混入碎屑”，引擎先记录这是待澄清的现象，而不是立即推荐某种刀头。第一轮可问碎屑是本次新产生的树皮屑、旧胶线残留，还是收集过程混入；这些回答将分别改变切割机理、清理步骤和收集链的研究重点。该例是提问设计，不能凭此认定实际客户污染原因。

若回答暂时不知道，引擎可以给观察取样方案或条件性分支，先使用R08/R50组织证据；不应要求用户自己填完全部方法字段，也不应把未知替换为默认事实。

## 缺输入的四种处理

| 缺的是什么 | 引擎应如何继续 | 不能做什么 |
|---|---|---|
| 对象和用途 | 少量追问，或辅助用户界定研究对象 | 未定对象就组合机构并宣布方案 |
| 可以检索的机制或案例证据 | 查找原理、记录源条件和迁移边界 | 把案例性能直接当客户目标 |
| 必须现场提供的工况、材料或测量 | 保留未知，列观察/量测任务；仍可做有条件概念分析 | 用语言模型估计关键工程参数当实测 |
| 专业求解或安全审核能力 | 交给对应工具或人员，停止超出能力的结论 | 把工具调用成功、脚本通过当工程批准 |

“停止强结论”不意味着停止全部研究。例如材料与载荷未知时，不能做确定性材料选型，却仍能建立功能模型、列出需要取得的数据并比较研究路线。

## 用户看得到的三层结果

1. **当前理解**：系统如何理解问题，哪些是用户明确说的，哪些是推测，允许修改。
2. **研究与方案**：为何使用这些方法，产物改变了什么判断，哪些路线被排除或暂留。
3. **依据与下一步**：原典/案例位置、未知、验证动作及需要谁参与；可展开核对，不以一大段内部JSON作为主要阅读方式。

## 系统内部需要的两道检查

**方法是否适合**：对照问题类型、阶段、工况、证据和工具。方法名相似只是检索线索，不是适用性结论。

**产物是否可信**：检查输入版本、关键判断依据、未知保留、输出解释范围和交接语义。能够产生整齐的表格，仍可能把偏好当物理事实、把教学假设当测量结果。

因此，方法深研应逐项产生可调用的知识和明确拒绝条件；前台则用少量有用的追问和可核对的解释呈现。它不要求用户先学会64份方法再开始研究。
