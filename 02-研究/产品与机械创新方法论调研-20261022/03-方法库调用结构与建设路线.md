# 方法库调用结构与建设路线
日期：2026-10-22｜平台设计建议，尚未实施。

## 1. 三种身份应分开
- research_id：本次R01–R48，仅用来定位候选。
- method_id + version：沿用现有IM方法身份，为真正可读取/运行的方法卡定位。
- run_id：一次调用/组合运行，不覆盖方法或源项目。

关系至少包括：part_of（子工具属于体系）、adapted_from（平台适配）、uses（依赖规则或数据）、precedes（通常衔接，不是强制）、alternative_to（解决同类问题的替代）、requires_tool（计算/测试依赖）。不把相关方法统统记成同义词。

## 2. 建议的扩展字段
保留现有method-card-1.0；下列为候选扩展，不能直接更改执行器契约。

| 字段 | 内容 |
|---|---|
| method_kind | framework / theory / method / tool / computational_method等 |
| lineage | 原作者、原典版次、流派、父体系；平台改编差异 |
| recognition_basis | 标准、专业组织、经典、研究，支持来源ID |
| read_scope | 摘要/目录/相关章节/全文；具体位置 |
| task_facets | 需求不清、原理单一、性能冲突、减件、接口、变异等 |
| input_schema | 类型、单位、必填、来源状态、允许未知与缺失处理 |
| execution_mode | 模型辅助/规则查询/检索/计算/真实用户研究/专家 |
| resource_dependencies | 数据集、矩阵、算法、软件和许可版本 |
| output_schema | 产物结构、假设与事实类型、依赖和证据 |
| applicability | 对象、尺度、材料、环境、目标、工艺、不可用条件 |
| decision_policy | 概念探索/工程建议/实施决策等允许层级 |
| evaluations | 结构检查、适用性反例、证据检查和任务效果评价 |
| status | 候选、原典核读、适配草稿、试用、审核等 |

不建议用一个“可信分”包办所有字段。来源清晰不等于输入可靠；输入可靠不等于步骤正确；步骤正确不等于方案经过工程验证。

## 3. 研究入库门槛
这些是平台建议，不是新增行政审批。

G0 研究候选：有明确身份和至少一项可追溯来源，保留核读范围。
G1 原典就绪：拟执行步骤的相关原典已核读，版本与权利边界明确。
G2 适配就绪：输入、步骤、产物、检查、停止与失败条件完整，注明平台改编。
G3 研究试用：用充分输入和反例跑通，并保存中间产物；只能称研究试用。
G4 任务评估：由合适领域人员评估适用性与实际帮助，保留分歧与失败。
G5 特定场景工程验证：有真实目标、工况、试验和可复查结论，不能泛化到全行业。

现有pilot_ready不因此自动升级；本包research_candidate也不能仅靠字段齐全改为pilot_ready。

## 4. 任务调用的最小输入
```json
{
  "task_id": "目标任务稳定ID",
  "task_revision": "目标要求版本",
  "actor": null,
  "object": null,
  "desired_outcome": null,
  "system_boundary": null,
  "operating_conditions": [],
  "requirements": [],
  "hard_constraints": [],
  "baseline": [],
  "evidence_refs": [],
  "unknowns": [],
  "decision_level": "concept_exploration"
}
```
空值表示未知，不是假设已确认。要求中的数值包括物理量、单位、比较符、容许范围和来源。把事实/实测/目标/假设分别标注。

## 5. 调度器需要回答的五件事
1. 当前任务缺什么，是否足以选择方法？
2. 为什么选这个方法，为什么暂不选其他方法？
3. 它需要读取哪些项目证据、机制或外部知识？
4. 本次只允许输出概念、条件性建议还是已验证结论？
5. 什么情况继续、追问、换方法或停止？

先以适用性和输入做过滤，再做检索或排序。不得仅因任务出现“轻量化”就自动执行TRIZ矩阵，或因为两个案例使用相同名词就判定可迁移。

## 6. 与项目库的联动
方法步骤提出查询：功能、作用原理、材料、尺度、工况、失败模式、接口、取舍、验证条件及原文证据。返回值至少包含：

- project_id、项目内容版本、源类型与可核位置。
- 原始陈述与平台机制解释分别返回。
- 适用工况和未覆盖条件、失败与代价。
- 方法调用中引用了什么，目标侧新增了什么假设。

先读目标硬约束，再读候选机制，最后决定是否需要更深原文。原项目仅某离散档位成功，不能扩写成连续适用区间。项目获奖、论文发表或专利授权均不自动证明目标适配。

知识库案例回看使用方法属于平台重构；除非有设计者直接记录，不写成“原团队当时采用本方法”。

## 7. 一次运行应保存什么
```json
{
  "run_id": "本次运行ID",
  "status": "draft",
  "task_ref": {"task_id": null, "revision": null, "sha256": null},
  "method_refs": [{"method_id": null, "version": null, "sha256": null}],
  "selection_rationale": [],
  "missing_inputs": [],
  "steps": [
    {
      "step_id": null,
      "input_refs": [],
      "operation_record": null,
      "tool_calls": [],
      "evidence_refs": [],
      "output_ref": null,
      "checks": [],
      "status": "not_started"
    }
  ],
  "outputs": [],
  "rejected_directions": [],
  "unknowns": [],
  "validation_plan": [],
  "actual_validation_results": [],
  "limitations": []

```
本结构只是讨论样例，不是已存在API。tool_calls须有真实请求与结果，不能补造。运行与方法引用固定版本；用户改变目标后标记受影响结论并重新评估，不悄悄覆盖旧结果。

## 8. 典型产物契约
- problem_brief：对象、目标、工况、边界、基线、硬约束、未知与决策层级。
- requirement_map：需求来源→工程响应→单位/阈值→验证方式。
- function_model：节点、功能、作用、输入输出、接口和证据类型。
- concept_set：不同原理、功能分配、接口、关键假设、被排除组合。
- contradiction_model：改善与恶化、因果依据、同一属性检验、映射与版本。
- mechanism_candidates：源机制、目标实现、相同点、差异、代价与失败边界。
- comparison：先筛硬约束、再比较；准则、权重、未知、证据和敏感性。
- validation_plan：假设、基线、操作、测量、通过/停止条件、资源与负责人。
- validation_result：实际执行、原始数据、结果、偏差和复核；不能拿计划填结果。

## 9. 建设批次
第一批：P0十二项；复用3张现有卡的范围，重点补形态学、FOS、筛选和验证产物。
第二批：FMEA、DFMA、DSM、公理化、材料选择、DOE、稳健设计。至少连接一套适当的计算/数据能力，再建立领域验证案例。
第三批：机构综合、拓扑优化、仿生专题、完整ARIZ、物场和进化趋势、C-K及研究型启发式。按明确场景逐一做，避免通用提示词冒充专业执行。
流程框架在编排层复用，不必为每个框架复制一遍全部工具。

## 10. 评估应怎么做
建议从六类任务起步：产品定义、性能瓶颈、减件降本、复杂接口、跨行业迁移、环境噪声下的不稳定。每类包含真实资料任务与一个明确不适用或缺输入的反例；数量是建设建议，不是已完成评估。

关注：
- 是否选到适合任务的方法，以及输入不够时是否正确追问。
- 是否真正产生不同作用原理，而非换名或换壳。
- 原文是否支持相关陈述，假设是否保留。
- 硬约束是否阻断，迁移差异是否被发现。
- 方案比较对权重与未知是否敏感。
- 验证计划是否可执行、可证伪、能对应目标。
- 用户或工程师是否认为它减少了遗漏、提升了判断质量。

软件检查只证明结构与程序行为；方法有效性须在任务和工程层评价。避免把回复长度、引用数、卡片数、方案数作为创新质量代理。

## 11. 本轮实际状态
本轮建立研究目录、来源台账和调用建议；没有实现调度器，没有增加线上方法条目，没有跑上述任务评估。现有方法库可用性与服务状态不因本报告自动改变。
