# 好设计：信息架构与平台定位 v2

2026-09-05。依据用户提供的完整压缩包，纠正v1把原版简化门户作为承接方案的问题。本版区分“现有资产”“建议结构”“后续建设”，后两者不代表已经开发。

## 一、定位建议

好设计是以优秀创新设计项目为核心的知识与应用平台。好设计奖提供项目来源与评价背景；项目库承载可追溯的事实与设计知识；好设计馆、科技教育、企业创新服务使用同一套项目知识。

现阶段先让已有产品完整运行，再把共享数据梳理清楚。长期可以发展创新设计智能能力，但“平台知识底座”与“训练一个基础大模型”是不同工程；先用现有模型、可检索知识与任务工具验证价值，更便于看清实际需要哪些专用模型能力。

## 三、建议的信息结构

### 用户看到的结构

```text
好设计平台
├─ 好设计奖：奖项介绍、评选理念、历届成果
├─ 项目库：全量作品、年度/奖项/领域筛选、项目详情
│  └─ 每个项目：事实 → 创新解读 → 相关知识 → 可用课例/展项 → 来源
├─ 好设计馆：主题展区、线上展厅、互动展项、线下馆应用
├─ 科技教育：项目课例、学科单元、教师备课、学生体验与记录
├─ 企业创新：提问题、找案例、做迁移分析、对接专业服务
└─ 智能助手：贯穿各页的辅助能力，也保留独立入口
```

本轮继续用原版馆首页；此树是后续导航讨论依据，不在此次上线大改。未来导航优先呈现“项目库、好设计馆、科技教育、企业创新”；奖项介绍作为品牌与来源入口。知识先放在项目上下文中，等形成稳定概念和检索任务后，再决定是否做独立知识门户。

“好设计馆”拥有独立体验，但应直接引用项目库的项目、图片、知识版本；教育和企业服务同理。一个项目可以属于多个主题、课程和应用，不应复制成互不关联的内容。

### 后台与数据的结构

```text
来源层：官方页、原件、访谈、会议、图片及使用范围
   ↓ 证据定位与版本
项目层：统一项目ID、奖项记录、单位、简介、媒体、领域
   ↓ 抽取与校准
知识层：问题、约束、原理、结构、方法、效果、适用条件
   ↔ 概念关系：解决/采用/受限于/适用于/类比于
   ↓ 按任务组合
应用内容层：展项包、课程包、企业迁移案例包
   ↓
服务层：浏览检索、问答辅助、备课、讲解、企业问题分析
```

治理贯穿全部层：事实/解释区分、来源与证据、审核人、版本、可用范围。后台按对象与工作流组织，不照抄前台菜单。

## 四、知识原子化如何落地

先定义一个完整项目知识包，再决定拆到多细。原子不是固定字数切片，而是可以独立引用、有证据、有使用条件的一条知识。

| 对象 | 最少需要的字段 | 用途 |
|---|---|---|
| Project 项目 | project_id、名称、单位、年份、领域、简介 | 跨所有应用保持同一身份 |
| AwardRecord 获奖记录 | project_id、奖项、年度、等级、来源 | 同一项目可能有多个获奖记录，不把奖项当项目主键 |
| Source 来源 | source_id、URL/文件、页码/段落、时间、公开范围 | 精确追溯与展示证据 |
| KnowledgeAtom 知识条目 | atom_id、project_id、类型、陈述、证据、适用条件、审核状态 | 支持可复用的知识检索和组合 |
| Relation 关系 | 起点、关系类型、终点、依据 | 找同类问题、相似方法及跨领域迁移 |
| ApplicationPackage 应用包 | 应用类型、关联项目/原子及版本、用户、任务、资源 | 同一底座生成不同展项与课程 |
| Review 审核 | 对象、版本、审核人、结论、时间 | 保留审核历史，更新后重新审查受影响产物 |

例：从一个机器人项目抽取“面对什么地形约束”“采用什么运动结构”“解决什么问题”“效果证据在哪里”“迁移到哪些场景需重新验证”。这些知识分别支撑展馆讲解、科学课探究和企业方案讨论，面向用户的表达可以不同，但来源不能丢。

优先复用现有项目ID并建立别名映射，先检查重名、跨年及重复获奖；不要直接重编560个URL。保留历史链接可减少后续维护成本。

## 五、两步推进

### 第一步：原版稳定上线（当前）

保留原视觉和页面，补齐遗漏的教师工具，恢复原助手与企业提交。平台不会因为这次迁移自动拥有完整知识检索、内容后台和用户系统。上线验收与迁移差异另见项目管理目录。

### 第二步：先验证知识复用，再扩平台

1. **数据归一**：核对项目、奖项、展区、案例、课例与拆解之间的ID和缺项；建立一份主项目清单，输出关联覆盖率。
2. **10个完整项目包**：选择已有资料较充足、能同时支撑馆和教育的项目；逐条保留来源、拆出知识、明确草稿与审核状态。样本数是建议，不是既定交付承诺。
3. **双应用验证**：同一个知识包生成一份展馆讲解/互动任务和一份教师课例，由实际使用者评估准确性与可用性。优先馆+教育；企业迁移保留试点入口。
4. **建设最小内容后台**：项目编辑、来源登记、原子审核、应用包版本；先解决内容维护，再扩大自动生成。
5. **升级助手**：按项目与来源检索，回答展示证据；用固定问题集测正确性、引用支持度和缺证据时的处理。再讨论领域模型与工具编排。

建议观察三类结果：项目资料/审核覆盖率；相同知识在两个应用中的复用与返工；教师备课和参观任务是否真的更容易完成。流量、原子数量和生成字数可以记录，但不足以证明平台价值。

## 六、下一轮讨论最值得定的三件事

- 首批服务谁：馆运营者与教师是否作为优先两类用户？
- 谁提供并审核项目资料：能否建立稳定的专家校准流程？
- 10个样本选择：优先资料完整，还是优先玉环当地产业及展馆主题？

我的建议是先用资料完整的少量项目跑通“项目→知识→馆/教育”的闭环，再带着真实样本确定玉环特色，而不是先把所有内容机械切成知识碎片。
