# GDRP 创新研究输出物标准 V0.1

日期：2026-11-05  
全称：GoodDesign Research Pack  
适用范围：产品创新、工程创新、AI4S 领域的概念创新设计引擎  
状态：标准草案与可校验示例，未改变现有生产引擎。

## 1. 核心定义

每一次研究任务完成后，系统必须交付一个**结构化、可阅读、可审核、可回放、可继续验证**的创新研究包。

研究包不是一篇生成文章，而是：

> 一个统一任务身份 + 一套结构化研究内容 + 一组领域扩展 + 一份人类阅读报告 + 一份机器可读 JSON + 一份文件完整性清单。

`recommendations=[]` 也可以是完整交付，表示当前不推荐，而不是研究包缺失。

## 2. 交付形态

每个研究包目录必须包含：

```text
<package_id>/
├── research-pack.json       # 结构化主数据，唯一内容真源
├── report.html              # 人类阅读版，由主数据生成
├── report.md                # 可编辑与审阅文本，由主数据生成
└── manifest.json            # 文件路径、SHA256 与包版本
```

可选增加：

- `evidence/`：允许交付的原文片段与定位，不放无权限原件。
- `figures/`：功能图、机制图、概念图和验证图。
- `domain/`：产品、工程或 AI4S 的专用附件。
- `feedback/`：后续客户、专家与试验反馈，不覆盖原研究包。

HTML、Markdown、图示和汇报页必须由 `research-pack.json` 生成，不能各自维护不同事实。

## 3. 统一骨架

| 部分 | 每次必有 | 回答的问题 |
|---|---|---|
| Task | 任务身份、领域、对象、版本与交付层级 | 在研究什么？ |
| Execution | 引擎、模式、方法、项目、模型与调用记录 | 怎样得出？ |
| Summary | 问题、已获得的研究结果、下一步与推荐状态 | 先看什么？ |
| ProblemBrief | 主体、场景、需求、约束、未知与验收口径 | 问题到底是什么？ |
| FunctionModel | 功能、流、接口和未知 | 需要实现哪些功能？ |
| CaseRetrieval | 查询、候选、来源、命中与未命中 | 哪些真实经验相关？ |
| TransferMap | 双侧机制、差异、假设、排除与证伪路径 | 什么能迁移，什么不能？ |
| ConceptSet | 功能选项、概念组合和相容状态 | 有哪些不同解法？ |
| Comparison | 准则、逐项判断、敏感性和推荐 | 当前能怎样选择？ |
| ValidationPlan | 决策门、变量、测量、停止与许可 | 下一步怎样验证？ |
| DomainExtension | 产品、工程或 AI4S 专用模块 | 领域还需要什么？ |
| Review | 客户、语义、领域、工程和公开状态 | 谁审到了哪一步？ |
| Boundary | 来源修改、试验、公开与训练权限 | 不能做什么？ |
| Manifest | 所有文件及指纹 | 怎样确认内容未变？ |

空数组可以存在，但必须有原因。未知不能静默省略，不能用空字符串、0 或中分代替。

## 4. 首页决策卡

人类阅读报告首页必须在不展开全文的情况下回答：

1. 当前研究对象与版本是什么？
2. 形成了哪些不同机制的研究候选？
3. 当前推荐、条件化推荐或不推荐是什么？
4. 哪些关键事实已经有证据，哪些仍是假设？
5. 下一步最值得做什么，由谁确认？
6. 当前是否允许工程执行、公开和训练？

割胶示例的首页结论是：形成 C1/C2/C3 三类候选，当前不推荐，先进入 G0 需求与现场基线确认。

## 5. 领域扩展模块

所有任务共用统一骨架，再按任务领域添加一个或多个模块。领域模块不得替代统一骨架。

### 5.1 产品创新模块 `product`

- `target_users`：目标用户与使用情境。
- `user_value`：用户可感知的价值与待验证收益。
- `journey`：关键任务流程与人工接管。
- `concept_architecture`：产品组成、功能与体验关系。
- `feature_priorities`：必须有、可以有、暂不做的功能。
- `mvp_scope`：最小验证产品范围及可撤销路径。
- `business_assumptions`：成本、价格、渠道、采用和维护假设，未知保留。
- `evidence_of_desirability`：用户证据与待验证问题，不能把 AI 分析当用户认可。

### 5.2 工程创新模块 `engineering`

- `system_boundary`：系统边界与外部对象。
- `technical_architecture`：技术系统与工作原理。
- `interface_register`：机械、电气、数据、材料与责任接口。
- `mechanism_options`：不同机制及适用条件。
- `engineering_risks`：失效模式、约束冲突与安全边界。
- `calculation_records`：真实计算、模型、输入、单位和复核；未计算为空并说明。
- `verification_matrix`：每项技术要求的验证方式与状态。
- `solver_results`：真实求解器及版本；语言模型输出不得放在这里。

### 5.3 AI4S 模块 `ai4s`

- `scientific_question`：需要解释或发现的科学问题。
- `hypotheses`：可证伪假设与变量关系。
- `mechanism_model`：科学机制、作用路径和适用条件。
- `variables`：自变量、因变量、控制变量和混杂因素。
- `data_plan`：观察、测量、仪器、样本、单位和数据质量。
- `experiment_design`：对照、重复、独立样本、随机化和停止规则。
- `uncertainty`：误差、统计与科学不确定性。
- `reproducibility`：数据、代码、模型、参数、环境和结果回放。
- `scientific_evidence`：支持、反驳与仍无法判断的证据，不能把生成文本当科学发现。

## 6. 交付层级与成熟度

统一骨架不代表所有任务都要达到同一工程深度。

| 层级 | 名称 | 可以交付 | 不得暗示 |
|---|---|---|---|
| L0 | 研究简报 | 问题、证据、机制、候选和下一步 | 已有产品方案 |
| L1 | 概念研究包 | 概念族、比较和验证计划 | 工程可行或客户认可 |
| L2 | 工程研究包 | 接口、风险、测量和验证矩阵 | 已完成工程验证 |
| L3 | 验证证据包 | 真实试验、用户反馈与结论范围 | 所有场景均有效或普遍可复制 |

L3 只能由真实记录形成，不能通过让模型补充内容升级。

## 7. 状态与审核口径

`review` 必须分开记录：

- `customer_confirmed`：客户是否确认需求与约束。
- `semantic_review`：语义与引用是否审核。
- `domain_expert`：领域专家是否审核。
- `engineering_validated`：工程验证是否完成。
- `public_authorized`：是否允许公开。
- `training_authorized`：是否允许训练。
- `overall`：综合状态，不得由单项自动推断。

模型和 Host 不得直接写 `customer_confirmed=true`、`engineering_validated=true`、`domain_expert=true` 或授权字段。

## 8. 机器校验规则

每份研究包必须通过：

1. JSON Schema 结构检查。
2. 任务、需求、概念、证据和文件 ID 唯一性检查。
3. 引用可解析，来源与版本匹配。
4. `hard=null`、`proposed`、`unknown` 不得被自动改写。
5. 每个非 `unknown` 判断必须有证据。
6. 硬门槛未通过或关键偏好未确认时推荐为空。
7. 验证计划不得包含未发生的实测结果。
8. 模型失败不得写成模型成功。
9. 所有文件 SHA256 与 manifest 一致。
10. 同一 `package_id` 不得覆盖，修订必须新建版本。

## 9. 人工验收问题

- 能否在两分钟内知道研究对象、候选、当前判断和下一步？
- 每个重要判断是否都能找到来源和适用范围？
- 候选是否来自不同机制，而不是改写同一方案？
- 是否明确写出不适用与无推荐的原因？
- 验证计划是否能区分变量、测量和停止条件？
- 产品、工程和 AI4S 的内容是否保持各自专业逻辑？
- 是否清楚哪些由 AI、Host、客户、专家或真实试验完成？

## 10. 割胶示例与标准文件

标准 Schema 与完整示例位于：

`04-知识库/项目档案标准-v1/创新研究输出物标准-v1/`

- `research-pack.schema.json`
- `examples/rubber-research-pack.json`
- `examples/report.md`
- `examples/manifest.json`

割胶示例使用真实研究产物，满足：15 项需求、7 个功能、28 个选项、4 个组合、60 个未知判断、`recommendations=[]`。它不是工程解决方案，而是 L1 概念研究包。
