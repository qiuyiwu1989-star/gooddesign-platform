# ML-026 方法资产与 Skill 规范

状态：approved（2026-11-05，用户确认继续；仅规范，未实施）

## 要什么

把64份方法档案升级为统一的方法资产：同一份内容真源驱动网页、Agent Skill、引擎/MCP、评测和版本治理。每个方法都有Skill，但按实际能力分为可读、引导和契约执行，不把文档包装成通用求解器。

## 不做什么

- 不重写或覆盖冻结v0.1内容，不批量新建64段独立Prompt。
- 不为每个方法新增一个MCP工具，不改变现有18/20/22工具入口。
- 不把框架、谱系专题强改成固定算法，不自动补原典缺失规则。
- 不以Agent评审、结构通过或调用成功替代专家审核、客户确认和工程验证。
- 本轮不实施生成器、不改生产、不接入真实客户数据或自动发布新版本。

## 复用与真源

- `深度方法库-v0.1.0/*/档案.json`及增补库：方法知识真源，沿用`method-dossier-1.0`。
- `执行契约-v0.2.0/*/contract.json`：六方法的严格产物与交接约束。
- `method_engine*.py`：统一读取、匹配、规划、检查、运行和模型工具。
- ML-021深化稿：内容候选与评测素材，未替换线上冻结正文。
- specs/098、099：执行三轨道与GDRP研究包，不另建平行输出标准。

Dossier、Contract、Evaluator是分别版本化的资产；Skill是由它们生成的操作视图，禁止手改生成稿形成第二真源。

## 方法资产模型

每项方法登记一个`asset.json`，最小字段如下：

```json
{
  "asset_schema_version": "method-asset-0.1",
  "research_id": "R42",
  "method_id": "IM-ML-042",
  "kind": "method",
  "content_ref": {"version": "0.1.0", "sha256": "<actual>"},
  "skill_level": "S2",
  "contract_ref": {"version": "0.2.0", "sha256": "<actual>"},
  "skill_ref": {"version": "0.1.0", "generator": "method-skill-0.1"},
  "evaluator_ref": {"version": "0.1.0", "sha256": "<actual>"},
  "review_status": "not_expert_reviewed",
  "validation_status": "not_engineering_validated"
}
```

规则：

1. `research_id`永久稳定；所有引用使用精确版本与SHA，不使用“最新”作为运行输入。
2. `kind`沿用现有值；框架、方法族、具体工具、计算方法和谱系专题不得混称。
3. 内容、契约、Skill、评测、引擎分别版本化；任何引用变化必须产生新资产快照。
4. 内容完成度、执行能力、评测状态、专家审核和工程验证分别保存，不合成一个成熟度总分。
5. 未知、无契约、无求解器、无真实结果必须显式表示，不能用空字符串或默认通过代替。

## Skill能力分级

| 级别 | 能做什么 | 不能暗示 |
|---|---|---|
| S0 可读 | 检索、解释、比较方法、返回来源与缺口 | 已执行方法或形成有效产物 |
| S1 引导 | 追问、组织步骤、形成带缺口的草稿或研究计划 | 契约通过、工程可行、自动提交 |
| S2 契约执行 | 按冻结Schema检查输入、产物、依赖和交接 | 专家认可、工程验证、普遍有效 |

`evaluation_status`独立取`unevaluated / benchmarked / context_validated`。评测升级不提高执行权限；`context_validated`必须绑定真实情境、证据和适用范围。

## Skill生成内容

每个`SKILL.md`使用标准`name/description`前置信息，正文只保留操作所需内容：

1. 方法身份、精确资产版本和适用边界。
2. 触发信号、不触发信号及替代方法。
3. 所需MCP工具、模型成本、外部访问和持久写入副作用。
4. 输入预检、缺失处置、执行步骤、返工与停止条件。
5. 对应`method_get/method_plan/method_check_*`等统一调用顺序。
6. 输出Artifact或引导草稿的类型、交接和结论上限。
7. 人工复核、反馈、真实Outcome补录要求。
8. 负例和评测入口。

正文通过引用读取完整Dossier和Contract，不复制整篇方法正文。平台专属策略需要变更时，必须进入新版本Dossier、Contract或生成模板，不直接修补生成后的Skill。

```markdown
---
name: gooddesign-r42-verification
description: 将已有要求与候选配置转成可追溯验证计划；不判定实测通过。

```

## 类型化模板

- `framework`：编排子方法、记录回返和决策，不强制所有阶段各运行一次。
- `method/tool`：按步骤生成中间产物，保留判断、证据与误用检查。
- `computational`：优先确定性计算器、单位和复算；缺模型或许可时降级定性。
- `lineage_framework_topic`：原典研究、平台适配和缺口分开，不重建未取得的原创算法。

模板采用白名单映射，不开放方法类型、角色、输出形态的全组合。

## MCP边界

继续使用统一`method_id + version`协议。S0/S1可以读取和记录引导过程，但不能调用严格提交冒充S2；S2沿用现有契约检查。步骤事件和反馈接口由ML-027定义，模型工具、只读工具和持久写工具的副作用不得混淆。

## 第一批实施范围

- 为R48、R14、R17、R36、R44、R42生成六个轻量Skill。
- 为R48、R17、R42建立完整资产清单和正/负例评测。
- R02、R22、R52、WB01只做S0/S1模板验证，不新增执行契约。
- 使用割胶固定样例回放；真实任务效果验证另走ML-024流程。

## 验收清单

- [ ] 64项目录均有唯一资产引用，缺失契约或评测显式为null，不伪报能力。
- [ ] 六个Skill由同一真源生成；改变Dossier指纹后旧Skill不可冒充新版。
- [ ] S0/S1严格提交被拒绝；S2缺输入、悬空引用和版本变化被阻断。
- [ ] R42“计划覆盖”不得显示为“已经验证”，R17未知相容性不得变成pass。
- [ ] R52缺概率与损失模型时只做定性分析，WB01不输出原典未核算法。
- [ ] 网页、Skill和MCP读取到的身份、版本与能力状态一致。
- [ ] 冻结60档案、六契约、原18/20/22工具入口和历史运行字节不变。
- [ ] 第一批Asset/Skill/Evaluator通过独立内容与接口复核后，才扩其余方法。

## 实现约束

新增生成器和检查器应使用现有Python 3、JSON Schema及项目测试体系；公开页面继续由构建产物生成。任何真实模型调用默认关闭，按需触发并记录成本。生产发布须另立发布任务并遵守当前磁盘与回滚限制。
