# 好设计创新研究引擎算法 V1（草案）

代号：GD-CRE-0.1  
日期：2026-11-05  
样板：割胶机器人研究任务 RUBBER-20261026 / r1  
状态：算法设计草案，未实施、未获客户或领域专家验收，不改变现有生产引擎。

## 1. 定义与边界

好设计创新研究引擎是以真实项目证据为基础，以设计案例推理为核心，以方法契约编排研究过程，以约束检查和验证计划收口的计算系统。

V1 不追求自动给出唯一最佳产品方案，而是把输入问题转化为：

`ProblemBrief + FunctionModel + CaseEvidence + MechanismOptions + ConceptSet + ComparisonRecord + ValidationPlan + ResearchRun`

V1 只做研究、概念和验证计划，不直接输出制造参数、工程许可、唯一技术定型、ROI、专家认证或实体试验指令。

### 1.1 核心计算命题

设计案例推理不是“相似项目有什么参数可以复制”，而是：

> 对目标问题与源项目进行机制映射，明确哪些设计思想可以形成候选，哪些差异会阻止迁移，以及应通过什么验证消除不确定性。

### 1.2 三条计算轨道

1. **确定性轨道**：需求版本、证据指纹、方法依赖、硬约束、未知状态、输出结构、保存与回放。必须执行，不依赖模型。
2. **研究推理轨道**：查询扩展、机制抽象、案例映射、候选组织和反例说明。可由 Host Agent 或受限模型辅助。
3. **真实验证轨道**：客户确认、领域审核、仪器、对照试验、用户反馈和授权回流。只能由人与真实过程完成。

模型不能代替第 1 轨道的校验，也不能冒充第 3 轨道已经发生。

## 2. 研究依据

- 经典案例推理采用 Retrieve、Reuse、Revise、Retain 循环。V1 扩展为“检索、映射、迁移、评价、验证、保存”，防止把复用误解为复制。
- 设计类比研究强调 Retrieval、Mapping、Transfer、Evaluation、Storage，以及功能、行为、结构之间的关系映射。V1 采用功能优先、机制映射和拓扑依赖，而非纯文本相似。
- NIST AI RMF 用于提醒有效可靠、安全、透明、可解释、隐私与人类监督必须进入设计和评价过程，不作为本项目认证。

## 3. 输入输出契约

### 3.1 输入

必需：

- `Task`：task_id、revision、对象、目标、研究边界、交付层级。
- `ProblemBrief`：主体、场景、需求、硬软属性、确认状态、验收口径、证据引用、未知。
- `CaseLibrary`：指定项目及研究版本，不默认读取全库最新版本。
- `MethodLibrary`：方法 ID、版本、输入、步骤、依赖、输出和停止条件。
- `ExecutionPolicy`：执行模式、权限、模型预算、允许结论层级。

禁止：

- 用企业名称代替真实需求。
- 把 `hard=null` 改成 `true` 或 `false`。
- 把 `proposed` 改成 `confirmed`。
- 用空字符串、0 或中分填充未知阈值。
- 默认接受真实客户任务已经完成确认。

### 3.2 输出

每次运行形成一个不可覆盖的 `ResearchRun`：

| 对象 | 内容 | 关键要求 |
|---|---|---|
| ProblemBrief | 问题与需求基线 | 保留确认状态、硬软未知与来源 |
| FunctionModel | 功能、流、接口和未知 | 功能不是零件清单 |
| CaseRetrieval | 检索词、候选、命中理由、未命中和缺口 | 区分逐字、语义、规则召回 |
| TransferMap | 双侧锚点、机制、差异、假设和排除条件 | 不复制源参数 |
| ConceptSet | 功能选项、组合与相容状态 | 不把理论组合数当研究数量 |
| ComparisonRecord | 准则、逐项判断、敏感性和推荐 | 允许无推荐 |
| ValidationPlan | 基线、变量、测量、步骤、停止与许可 | 计划不等于已验证 |
| ResearchRun | 输入、版本、调用、模式、错误和产物指纹 | 可回放、不可覆盖 |

## 4. V1 算法步骤

### S0 预检与执行模式冻结

检查任务、研究版本、权限、方法版本和预算。

执行模式只能是：

- `rule_only`：确定性结构和规则，不调用模型。
- `host_agent`：Host 负责研究推理，工具读取和校验真实执行。
- `model_assisted`：受限模型辅助研究推理，工具禁用、结构输出、预算固定。

模型失败必须记录失败及后续 Host 路径，不得把 Host 产物写成模型自动生成成功。

### S1 需求结构化

将原始输入转成 ProblemBrief，保留：

- 需求 ID 和文本。
- `hard=true/false/null`。
- `status=proposed/confirmed/unknown`。
- 验收口径与目标值，未知为 `null`。
- 证据、来源范围和未知。
- 有权确认的人及批准状态。

割胶输入为 15 项需求，全部 `proposed`，`approved=false`。N04/N05/N06/N08/N09/N10/N11/N12/N15 的硬软属性为 `null`，其余硬要求建议也只是 `proposed`。

### S2 功能图与接口建模

把问题转成动词加对象的功能，并建立物料、能量和信号流。

割胶功能图：

- F1 识别对象并建立局部轨迹。
- F2 约束切入与耗皮。
- F3 完成受控切削。
- F4 排出并隔离切屑与旧胶线。
- F5 监测异常并安全退出。
- F6 清理、更换与复核配置。
- F7 导流收集并记录作业。

F1 的表面几何参考不能直接变成 F2 的内部安全深度；F3 的切屑与胶乳分别进入 F4 与 F7；F6 复装后必须重新确认基准。

### S3 生成检索计划

按功能、机制、约束和边界生成查询，不只按行业或企业名称检索。

每个查询保存：

```json
{
  "function_id": "F2",
  "intent": "寻找几何适应、力位协同与限深边界的不同处理机制",
  "query_terms": ["仿形", "力位协同", "几何适应", "剩余材料", "限深"],
  "required_dimensions": ["mechanism", "boundary", "verification"],
  "exclude_as_proof": ["源项目恒力或传感参数直接成为目标安全深度"]
}
```

V1 支持三类召回：

1. `literal`：现有逐字短语和字段优先级。
2. `structural`：问题、功能、机制、验证和边界字段筛选。
3. `semantic`：可选模型或向量扩展同义表达，仅用于召回，不能自行增加事实。

### S4 案例召回与分层排序

每个功能先召回最多 8 个候选，再做项目去重和机制多样化。V1 不使用未校准的单一相似度分数，采用可解释分层：

1. 证据是否可定位、版本是否匹配。
2. 是否命中当前功能或相近问题结构。
3. 是否具有可抽象机制，而非只有产品名称。
4. 是否能明确源项目边界和目标差异。
5. 是否提供不同机制，避免同一项目占满候选。

候选状态：

- `option_candidate`：可以形成研究选项，仍需目标验证。
- `research_only`：只提供问题或验证启发，不进入功能选项。
- `excluded`：对象、目标、硬约束或权限明确不适配。
- `unknown`：证据不足，不能判断。

未命中只表示当前检索没有结果，不证明没有相关知识。

### S5 机制抽象与双侧映射

每条 TransferMap 必须包含：

```text
source_case / source_revision / source_anchor
target_function / target_revision
mechanism
transfer_kind = structure | workflow | control_strategy | validation_strategy | explanation
similarities
differences = object / medium / scale / constraints / measurement / authorization
required_assumptions
not_transferable = parameters / thresholds / materials / controller / claims
status = option_candidate | research_only | excluded | unknown
falsification_path
```

割胶中的典型映射：

| 目标功能 | 源案例机制启发 | 明确不能迁移 |
|---|---|---|
| F1 几何定位 | 复杂铸件磨抛对非规则形体分别处理定位、路径与材料响应 | 铸件余量不是树体安全边界，外形扫描不证明内部厚度 |
| F2 切入控制 | 柔性焊接的力位协同与过程监测分开建模 | 金属连接与可控生物损伤目标不同，恒力不等于限深 |
| F4 物流分离 | 苹果采摘将获取动作与输送收集分开 | 果实与枝条分离不等于树皮采胶，不采用拔离树皮动作 |
| F5 异常退出 | 嫦娥采样复用驱动状态并考虑故障预案 | 不用钻具、功率裕度或电流单独判断树体安全 |
| F7 收集与品质 | 采样目标不只追求数量，还关注品质和工况覆盖 | 真空颗粒与黏弹树皮、胶乳不同，不搬任务阈值 |

### S6 功能选项形成

每个功能最多保留 4 个选项：

- `O0`：客户现状待采集占位，不代表已测基准。
- `O1`：以机械、结构或流程为主的选项。
- `O2`：以感知、控制或监测为主的选项。
- `O3`：以人工判断、人机协作或渐进改造为主的选项。

每个选项必须绑定证据或明确标为研究假设，并写出条件和不适用边界。

割胶形成 7 维、每维 4 个选项，共 28 个选项。`4^7=16384` 只是理论笛卡尔空间，不能宣称已经研究 16384 个方案。

### S7 概念组合与约束剪枝

V1 采用少量有明确机制差异的概念族，不做全量穷举：

- C0：客户现状占位。
- C1：机械参考、双物流隔离和可复核限位。
- C2：感知辅助、过程状态与安全边界分别处理的闭环末端。
- C3：人机协作和低负担接管的渐进改造。

只有已确认硬约束才能直接排除组合。未知相容性保持 `unknown`，成对相容也不能推出整体工程可行。

### S8 逐项比较与推荐门禁

比较准则由需求生成，保留需求版本和硬软原值。判断值只能是：

- `pass`：同条件证据满足已确认判据。
- `conditional`：只有特定条件成立才可用。
- `unknown`：缺少证据或判据。
- `conflict`：违反已确认硬约束。
- `not_applicable`：该准则不适用且有理由。

推荐必须同时满足：

1. 所有必需硬约束已确认。
2. 没有 `conflict`。
3. 关键判断不是 `unknown`。
4. 用户偏好和比较准则已确认。
5. 目标工程验证达到当前交付层级。

割胶 4 个概念 × 15 项准则形成 60 个判断，当前全部为 `unknown`，`recommendations=[]`。这是 V1 的正确输出，不是算法失败。

### S9 生成验证计划

验证按决策门组织：

- G0：需求、现场基线、口径、许可与责任确认。
- G1：非活树或替代件的机构、物流和退出检查。
- G2：经许可的局部机制对照，区分随形、切削、胶线处理等因素。
- G3：受限现场试点，记录完整周期、品质、损伤、异常与人工介入。
- G4：跨周期树体影响、维护、成本与真实采用。

每项计划包含：假设、变量、对照、测量、配置、样本独立规则、停止条件、专业批准和结果状态。

同一棵树多次刀次不能冒充独立树株样本，替代件不能证明活树安全，短期试验不能证明季节产量与长期树体健康。

### S10 保存、回放与有限回流

每次运行保存：

- 任务与需求指纹。
- 项目、方法、证据和模型实际版本。
- 查询、返回、未命中、排除和错误。
- 执行模式、模型预算和人工参与。
- 所有产物及文件指纹。

反馈只形成新需求或新运行版本。不得自动修改源案例事实、分数、专家状态或公共知识。

## 5. 算法伪代码

```python
def run_engine_v1(task, case_library, method_library, policy):
    brief = validate_problem_brief(task.problem_brief)
    require_not_silently_confirmed(brief)

    functions = build_function_graph(brief)
    queries = build_queries(brief, functions)

    transfer_options = []
    for function in functions:
        candidates = retrieve_cases(
            queries[function.id],
            modes=["literal", "structural"] + policy.semantic_modes,
            limit=8,
        )
        for case in diversify_by_mechanism(candidates):
            mapped = map_mechanism(case, function, brief)
            if mapped.status != "excluded":
                transfer_options.append(mapped)

    options = group_options_by_function(transfer_options, include_baseline=True)
    concepts = compose_concept_families(options, strategy=["mechanical", "closed_loop", "human_collaboration"])
    concepts = prune_only_confirmed_hard_conflicts(concepts, brief)

    comparison = compare(
        concepts,
        criteria=brief.requirements,
        preserve_unknown=True,
    )
    comparison.recommendations = recommend_only_when_gate_passes(comparison, brief)

    validation = build_validation_plan(
        hypotheses=concepts,
        requirements=brief.requirements,
        unknowns=comparison.unknowns,
    )

    return freeze_research_run(
        brief, functions, transfer_options, concepts, comparison, validation,
        execution_mode=policy.mode,
    )
```

模型只能参与 `build_queries`、`retrieve_cases` 的语义召回、`map_mechanism` 和 `compose_concept_families` 的提议。其余状态与门禁由确定性代码控制。

## 9. 验收标准

### 9.1 结构与追溯

- 15 项需求均保留原硬软与确认状态。
- 7 个功能、28 个选项和 4 个组合均有来源或研究假设标记。
- 每个案例引用能回到项目、版本、来源和片段。
- 每次运行可重放并核对输入与产物指纹。

### 9.2 必要负例

- `hard=null` 不得被改成 true/false。
- 相似但不适用案例必须能排除或降为 research_only。
- 源项目参数、阈值和控制增益不得进入目标规格。
- 缺少偏好与硬软确认时推荐必须为空。
- 版本变化不得继续沿用旧输出。
- 模型失败不得被写成模型成功。
- 不得把 16384 理论组合说成已研究方案。

### 9.3 研究质量对照

沿用 ML024 四组：

- A：通用模型基线。
- B：模型加案例经验。
- C：模型加方法。
- D：模型加案例经验和方法。

比较问题理解、证据支持、机制推导、约束覆盖、候选差异、验证可执行性、人工修改量和实际成本。小样本只描述本次结果，不宣称普遍优势。

### 9.4 领域放行

技术通过不自动等于语义正确、客户认可或工程有效。G0 未完成前只能内部研究；农艺许可、安全判据、专业监督与现场条件未具备时不得对活树试割。

## 10. V1 实施顺序

1. **确定性骨架**：先跑通无模型的输入、检索、映射、组合、比较、验证和不可覆盖运行。
2. **割胶固定夹具**：把 15/7/28/4/60 及 recommendations=[] 做成回归基线，加入负例。
3. **Host 审核工作流**：人能修订映射、排除选项、确认需求和冻结研究版本。
4. **混合召回**：再增加语义召回，测量召回率、误召回和人工修改量。
5. **真实任务对照**：用少量已确认问题检验引擎是否比通用模型更有增量。
6. **后续学习**：只有积累足够真实审核记录后，才考虑学习排序、专用模型或微调。

V1 的成功标准不是“自动发明割胶机器人”，而是证明：同一套算法能稳定地产出证据充分、差异明确、没有越界结论、可供人与真实试验继续推进的研究包。
