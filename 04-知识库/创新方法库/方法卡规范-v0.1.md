# 方法卡规范 v0.1（提议）

## 面向人阅读，支持引擎逐层调用

页面默认显示：方法名称、一句话用途、何时适用、何时不适用、主要输入输出；展开后显示步骤、示例、检查标准和来源。不把提示词、运行参数或冗长研究过程堆到正文。界面和调用都读取同一方法卡及版本，避免形成两套解释。

## 一个方法卡的组成

| 区域 | 关键内容 |
|---|---|
| 身份与出处 | method_id、版本、名称/别名、作者/原典、原始/改编/平台自定义、来源定位与使用权限 |
| 作用与选择 | 适用任务、阶段、触发条件、前提、不适用条件；缺少哪些输入时应追问或停止 |
| 输入 | 必填/可选项、类型、单位/口径、允许的未知状态，以及用户提供/项目库取回的来源 |
| 操作步骤 | 稳定step_id、目的、依赖步骤、操作、需调取的知识、预期中间产物、检查点与停止条件 |
| 知识调用 | 检索的问题/功能/约束，目标实体或关系、证据要求、排除条件、允许的分析性质与上下文预算 |
| 输出 | 结构化产物、解释、证据、假设和验证计划；不承诺每次都必须产生创新方案 |
| 质量与边界 | 完成条件、常见误用、反例、待验证假设、与其他方法的衔接条件 |
| 版本与评估 | 审读状态、修改理由、评估题目/结果、失败案例和适用范围变化 |

外部原典、平台改编及执行提示词分别标记，不能把AI补写步骤当成原作者原文。案例可以有“平台认为可用某方法解释”的映射，但不能据此声称研发团队真实使用过该方法。

## 与项目知识库如何结合

1. 需求形成独立任务记录：用户目标、现状、硬约束、已有信息、成功标准及待回答问题。
2. 引擎选择方法时说明理由、前提和替代方法；缺失关键输入则追问。
3. 按具体步骤检索项目知识单元：优先问题/功能/约束，随后机制、试验及证据，最后按需读取原文。
4. 记录方法步骤与知识单元之间的调用关系，保存双方稳定ID、版本、证据位置和本次使用理由。
5. 每个推演结论说明它依赖哪个事实、使用哪个方法步骤，以及新增了哪些目标场景假设。使用方法不自动使结论成立。
6. 应用结果独立保存。验证过的经验经过审核可回流为方法适用范围/反例或项目关联记录；不把目标应用假设写回源项目事实。

## 执行记录的最小要求（后续实现）

run_id、task_id、需求版本、method_id/method_version、step_id、知识单元ID/版本、证据引用、输入缺口、选择理由、intermediate_outputs、assumptions、conclusions、检查结果、review_status、validation_status、执行主体/模型与时间。

方法组合必须说明：前一步的哪项输出，满足后一步哪项输入。用多个方法名装饰同一段答案，不算完成了组合。

## 质量评价

分开记录：原典可追溯、步骤可执行、知识调用可解释、产物可核查、任务验证表现。方法是否标准化、是否在测试中有效、是否适用于本次企业任务是三个不同判断，不合并成没有校准依据的通用分数。

优先用真实需求测试：能否暴露原来遗漏的约束；不同操作者能否依规执行；关键结论能否追溯；遇到反例能否停止或更换方法；是否形成可验证的下一步。比较方法/提示词版本时固定任务与知识快照，并保存失败结果。

## 接入边界

当前仅规范、空目录及模板。未来可提供方法检索、分层读取、执行计划与运行记录接口；这些尚未实现，不能把当前项目MCP称为已包含方法库。先用一个需求跑通少量方法与嫦娥知识单元的组合，再确定接口。
