# 结构化项目档案与深度研究规范 v3.0

状态：试行字段合同；不是已投产数据库，也不代表项目事实已完整核验。2026-10-19。

## 目的与分层

一个项目的档案应能直接阅读，也能逐项查询和跨项目比较。八个板块是阅读结构；17类实体是可重复登记的记录；233个原子字段是研究要求，不是页面必须同时展现的233个输入框。

正文保留12维度、49个复合字段与22标签，承载完整解释。原子字段承担精确的数据表达。来源台账保存证据，不能以字段字典替代项目方原始材料。

项目→获奖记录、机构角色、人员角色、需求问题、技术系统、指标、创新机制、专利、论文、成果统计、事件、验证、应用、故事、来源、维护任务。实体用稳定ID关联，显示顺序和项目标题不能用作主键。

## 八个阅读板块

| 板块 | 记录内容 | 优先回答 |
|---|---|---|
| 身份、获奖与团队 | 项目、奖项、机构、人员 | 是什么项目，哪年获什么奖，谁完成？ |
| 需求与技术系统 | 问题、技术 | 为谁解决什么问题，采用什么系统？ |
| 创新机制与方法 | 创新点与对照 | 改了什么，为何有效，有什么代价？ |
| 指标与验证 | 指标、试验 | 数值属于谁，在什么条件下如何验证？ |
| 专利、论文与成果 | 专利、论文、其他成果与统计 | 找到什么条目，归属与权利确认到哪一步？ |
| 历程与设计故事 | 事件、故事 | 何时发生什么，设计决策如何形成？ |
| 应用、价值与迁移 | 应用记录与分析 | 实际用于哪里，收益有哪些证据，能迁移什么？ |
| 证据与持续维护 | 来源、补证、审核 | 每个判断依据什么，还缺什么，由谁继续？ |

## 核心字段怎样调查

**获奖记录**：一项目可有多条奖项记录。登记年份、届次、奖项名称、等级、主办方、官方编号、完成单位引用、完成人引用、证书/名单证据、获奖日期与公开摘要。年份只有2025就记录2025，不能补成2025-01-01。正式完成单位、承研单位、供货单位和申请人分别登记，报道涉及人员不等于获奖完成人。

**专利条目**：一项申请独立建档。申请号、公开公告号、授权公告号分列；同时登记名称、类型、申请日、公开日、授权日、原文申请人、当前权利人、发明人、法域、IPC/CPC、同族、法律状态与状态核验日、权利要求定位、项目关系及依据、关联创新点、许可条件。公开文本记载的申请人不能直接写成当前权利人。A/B文献通常是同申请不同阶段，不能按两件专利相加；申请人/发明人相同也不能据此确认项目归属。

**论文条目**：题名、作者及顺序、通讯作者、单位、发表年份、网络发表日、期刊/会议、卷期页码、DOI、链接、问题、方法、结论、阅读程度、项目关系与依据。DOI中的年份不自动作为出版年份；只读摘要时，不写成全文核验。外部参照文献独立标识，不能计入项目正式成果。

**数量统计**：披露总量、实际找到条目数、项目确认关联数、完整清单状态分别表达。披露数必须带统计主体、范围、时间、单位和来源；未知统计截止日保留未知。确认数量未知不等于0。跨机构专利不能简单相加，同族去重与申请件数也不是同一口径。

**技术指标**：指标名称、对象、版本、数值、单位、限定词、数据性质、工况、方法、样本量、对照值、测量日期、原始口径和不确定性一起登记。要求值、实测值、仿真值、来源披露不能混作性能结论。“约1731g”“小于5%”中的限定词必须保留。整任务与子系统结果分别记录。

**创新点**：问题、措施、机制、对照、效果指标、代价、失效边界分别表达。平台提出的机制解释标为分析；效果缺证时留空，不用推理补成实测成果。

**发展、验证与应用**：事件保存日期精度、对象范围和发生状态；试验保存目的、装置、方法、对照、样本、指标与局限；应用保存版本、客户/场景、成熟状态、规模、收益及其计算依据。历史任务成功不能直接推出商业收益。未来展馆、课程、企业迁移建议放分析层，不能当已实施案例。

**故事与人员**：区分公开报道、亲历访谈和平台整理。故事保存原文或整理叙事、人物、决策、过程、证据与访谈状态，不虚构动机、困难或个人贡献。跨项目共享人员与机构时，项目角色是关系属性。

## 每个字段值的证据封装

`value`保存值；同一对象并存信息状态、内容性质、来源ID、事实条目ID、精确定位、核验状态、有效截至与可见范围。记录ID在外层；跨项目关联通过ID表达。研究元信息和原始事实各有性质，自动统计或平台任务必须保存推导规则。

- `known`：已有具体值；不等于经过专家确认。
- `not_researched`：尚未调查此项，值为null。
- `not_obtained`：调查后尚未取得所需资料，值为null。
- `not_applicable`：有理由不适用，说明理由，不填0或空字符串。
- `conflicting`：存在冲突；保留各来源主张，不能随意合并。当前单值结构仅能标记冲突，后续数据库需独立主张表。

核读、交叉验证、项目方确认、专家审核应分别记录。本例目前只有来源核读及平台登记；未达到专业审核。资料访问日期不是事实有效日期，故有效截至不从访问日期自动填入。当前原子档案默认为内部研究，公开来源也不自动授权再发布全文或图片。

日期采用ISO日期或明确精度的部分日期。数值和单位分列，数量保持整数；未知数量为null。可枚举字段目前是带语义约束的试行文本，尚未全部冻结为闭合集合；全库导入前应完成词表归并、同义词映射与版本迁移，不能宣称现有文件就是完整JSON Schema。

## 研究优先级与新项目作业

P0共107项，表示对应实体适用时必须调查；不是必须编造一个值。P1按领域与资料条件扩充。月球采样的6个专用扩展不要求所有项目填写。一个没有论文的作品应记录适用性调查结果，不建立虚假的空论文条目。

1. 确认项目身份、奖项与研究边界，查重并建立稳定ID。
2. 按八板块列资料清单，先调查适用实体的P0；来源同时登记读取范围与位置。
3. 为实际找到的奖项、专利、论文、指标等逐条建记录，保留来源原名。
4. 调查项目关系、权属、统计口径，不能以关键词匹配替代确认。
5. 整合正文与创新解释，保持分析和来源陈述分开。
6. 检查缺口、冲突与不适用理由，形成有验收条件的补证任务。
7. 项目方及领域专家审核后再提高审核等级，变动保留版本。

“调查完成度”应统计适用字段的调查状态及证据等级，不能用已填字段数除以233。研究全网资料不意味着获得全部资产、权利或项目方认可。

## 展示设计约定

保留现有纸色背景、深绿强调、金色编号及宋体标题；不重做整站。默认八板块，左侧直接定位；奖项与机构采用卡片，专利/论文/指标采用表格。单条卡片占满可用宽度，多条桌面两列、手机单列。长表格在自身容器横向滚动，不撑宽页面。

默认显示主要字段，其余字段折叠；每个已填值可展开依据。字段名称是按钮，进入字段定义；定义提供研究问题、类型、优先级、适用范围、证据要求及本例值反查。ID作为高级查看选项。搜索空结果提供清除筛选；跳转打开父级折叠并聚焦目标，按钮原生支持键盘。打印保留完整正文及来源目录，避免重复打印全部字段字典。

## 文件与维护

- `原子字段字典-v3.json / .csv`：字段规范，含全部233项定义；CSV用于分工和后续研究表。
- `scripts/build_case_field_standard.py`：字段规范的编辑入口。
- `scripts/build_case_atomic_data.py`：本例证据→原子值的显式映射，新增事实先更新证据真源，再维护映射；不得直接手改生成JSON。
- `scripts/render_structured_case.py`：分板块与字典展示。
- `python3 scripts/build_benchmark_dossier.py`：统一重建规范、原子档案、正文与页面。
- `python3 scripts/check_structured_case.py`：类型、空值、引用、实体关系、定位及数量口径自检；不是事实独立审查。

当前文件映射是研究基线，不是在线编辑器、自动全网研究、生产数据库或完整生命周期服务。下一步先用第二个不同领域案例试填并校准词表，再确定数据库关系、修订历史和批量研究作业。
