# 好设计项目文档文件结构规范 v1.0

2026-10-20｜以嫦娥月球钻取采样系统读者版为样本｜适用于后续项目建档

一个项目是一份完整文档。读者从三个入口阅读同一项目，维护人员在背后管理数据、来源与版本；不同入口不另建一套事实。

本规范确定文档组织与文件职责；233项字段的类型、适用性和逐值证据继续执行既有字段规范。本次不迁移嫦娥文件，也不表示新目录已接入现有构建程序。

## 一、读者看到的文档结构

```text
项目名称 / 项目编号
├── 项目首页：一句话介绍、概述、获奖信息、整理日期、审核状态
├── 01 项目档案
│   ├── 总览：项目示意、八模块入口、记录/资料统计、质量自评
│   ├── 1 项目概况
│   ├── 2 需求与系统
│   ├── 3 设计思路
│   ├── 4 指标与验证
│   ├── 5 专利与论文
│   ├── 6 历程与故事
│   ├── 7 应用与价值
│   └── 8 质量与维护
├── 02 资料与解读：论文解读 → 其他重点资料解读 → 参考资料目录
└── 03 档案评估：质量评价 → 模块统计 → 补充清单 → 审核与更新记录
```

三个入口共用项目标题、左侧阅读目录与正文宽度。模块按需展开；来源说明、原始试验表与研究细节放在第二层。首页先帮助人理解项目，不铺开全部字段。

### 八模块的标准内容

| 模块 | 必须回答的问题 | 建议结构化内容 | 默认适合的呈现 |
|---|---|---|---|
| 项目概况 | 这是什么项目，谁做的，获得什么认可？ | 稳定项目ID、规范名/别名、研究范围/排除范围、版本关系、获奖记录、完成单位/人员及贡献依据 | 简介、身份属性、奖项卡；完成人与报道牵头人分开 |
| 需求与系统 | 为什么做，面对什么条件，怎样工作？ | 用户/场景、原有方案、问题、目标、约束、系统组成、关键部件、材料/工艺/控制、接口 | 问题与目标卡、系统或流程示意、参数属性 |
| 设计思路 | 最关键的设计决策是什么，为什么有效？ | 原问题→措施→机制→结果依据；备选方案、取舍、失败、适用条件、边界、方法映射 | 一条思路一张卡；原理/代价/边界展开阅读 |
| 指标与验证 | 效果如何，在哪些条件下得到？ | 对象/版本、指标原值/单位、基线、工况、样本、测量方法、时间、验证主体、结果/限制、来源定位 | 关键结果优先；部件/地面/任务/应用分组，完整表折叠 |
| 专利与论文 | 有哪些成果，能否确认属于本项目？ | 披露总数/找到数/确认归属数；专利申请/公开/授权号、权利人与状态日期；论文题目/作者/年份/DOI/阅读范围 | 成果统计、简明目录、解读跳转；候选与确认分开 |
| 历程与故事 | 怎样发展，哪些决策改变了结果？ | 日期及精度、事件、阶段、人物组织、决策、失败/修正、版本、来源；原话与平台叙事分开 | 关键时间线、可展开故事 |
| 应用与价值 | 哪里已经应用，哪些经验可能迁移？ | 已证实应用、主体/规模/日期/效果口径；迁移问题、前提、差异、代价、假设、最小验证 | 已发生与未来设想分区；不把类比假设当作转化成果 |
| 质量与维护 | 这份档案目前可靠到什么程度？ | 质量自评摘要、审核状态、主要缺口、负责人/复核日期、版本入口 | 简短质量卡与待补提示，详细依据链接到档案评估 |

“质量与维护”只展示摘要；完整评分依据只维护一份，在“档案评估”中查看。项目中的论文目录与资料页中的论文解读共享同一论文ID，不复制成两个成果。

## 二、实际文件目录

```text
<稳定项目ID>-<项目简称>/
├── README.md                     # 项目说明、入口、研究边界、维护办法
├── 项目清单.json                 # 项目ID与文件角色登记，不存另一份项目事实
├── 01-项目档案.md                # 面向人的八模块正文 / 写作提纲
├── 02-资料与解读.md              # 解读及参考资料目录
├── 03-档案评估.md                # 质量依据、缺口和审核说明
├── 数据/
│   ├── README.md                 # 真源与生成文件职责；共享字段规范位置
│   ├── 档案数据.json             # 事实记录、来源、论文、专利、事件等真源
│   ├── 主档案结构.json           # 人工整合正文真源
│   ├── 阅读内容.json             # 平台解读真源
│   ├── 质量评估依据.json         # 人工/审核评分依据真源
│   ├── 研究日志.json             # 查了什么、阅读范围、未找到什么
│   ├── 原子字段档案.json         # 生成：逐值结构、状态与证据
│   ├── 质量评估.json             # 生成：按量规计算结果
│   └── 阅读统计.json             # 生成：各模块记录与已填项统计
├── 来源/
│   ├── README.md                 # 来源卡、原始附件与可见性规则
│   └── S编号-来源简称.md         # 一份来源一张卡，保留URL与原文定位
└── 版本/
    ├── README.md                 # 冻结及修订规则
    ├── 更新日志.md               # 面向人的增删改摘要
    ├── 版本索引.json             # 有真实冻结版本后再生成
    └── <内容版本>/               # snapshot.json + changes.json + manifest.json
```

上图是完整目标结构。新项目先复制模板中的少量文件；未开展研究时不造假数据、不造评分、不造版本快照。数据文件按研究进展与实际构建流程建立，不要求建档当天就填满。

- 一个项目一个根目录，不因获奖年份增加一份重复技术项目；奖项作为独立记录关联。
- 正文八模块放在一份文档，初期不拆成八套子目录。
- 发布HTML/PDF是可重建导出物，统一放平台发布/导出位置；不要把打包网站代码复制到每个项目里。
- 项目图谱、企业迁移演示等为可选派生应用，绑定来源项目与内容版本，放平台应用区；不把割胶机器人等新课题写成嫦娥原项目成果。
- 原始PDF、会议全文、访谈、图片/视频放项目的内部原始资料区（本平台为`01-原始资料/`），来源卡登记路径、哈希及使用范围；目录结构不授予公开权限。

## 三、谁是唯一真源

| 信息 | 编辑位置 | 其他位置如何使用 |
|---|---|---|
| 来源陈述、成果题录、事件、项目关系 | 数据/档案数据.json | 原子数据、正文引用、图谱引用，不各存一份手改值 |
| 整合后的主档案正文 | 数据/主档案结构.json | 生成项目档案MD/HTML；展示章节可组合多个字段 |
| 论文解释与阅读摘要 | 数据/阅读内容.json | 生成资料与解读；明确实际核读范围 |
| 评分理由、等级、审核人 | 数据/质量评估依据.json | 生成质量评估与阅读页，不手改总分 |
| 检索过程与未取得资料 | 数据/研究日志.json | 支撑缺口说明，“未找到”须有检索范围 |
| 来源详情 | 来源卡及档案数据中的来源记录 | 以同一source_id关联；卡片解释与索引元信息一致 |
| 统计、原子字段、索引、评分计算 | 构建程序生成 | 禁止为凑数或好看而手改输出 |
| 历史版本 | 版本/<内容版本>/ | 冻结后不可覆盖，纠错形成新版本 |

模板中的三份MD目前是可直接使用的研究写作提纲，尚非已接入构建的导出物。进入平台结构化流程时，先将内容录入上述真源并核对，再生成MD/HTML；不要长期并行手改两份正文。新目录构建适配是后续工作，不能直接用当前硬编码嫦娥的脚本构建新案例。

## 四、关联与索引

稳定关系为：`项目 → 模块 → 字段/记录 → 陈述/解读 → 来源与原文位置`。反向也应能从来源找到受影响的字段与解读。

- 永久项目ID不随标题变化；记录ID在项目内唯一，跨项目使用`项目ID:记录ID`。
- 沿用来源S、关键陈述C、专利P、论文A、机制K等现有ID规则；章节01/02只是显示顺序，不作永久引用ID。
- 一个数值必须知道“什么对象、哪个版本、什么单位、什么工况、谁提供、哪里找到”；无法取得的部分留缺口。
- 未知值用null并保留原有value_state，不把0、空字符串或“无”混为未知；页面可以留空或收起待补字段。
- 事实、平台解读、迁移假设和验证结果分开标注；论文只读摘要时不标全文，候选专利不计已确认归属。
- 引擎用设计机制时，读取问题、约束、措施、取舍、适用条件、证据边界与待验证事项；方法映射是平台解释，不能倒写成项目团队真实使用了TRIZ。

## 五、评估与生命周期

建档 → 研究 → 整合 → 结构检查 → 平台自评 → 项目方/专家审核 → 持续维护。研究进度与审核状态分别记录，不以单一“已完成”代替。

每轮记录新增、修订、删除/撤回的内容与原因、操作者、日期、受影响字段和输出；内容冻结、页面布局、字段字典、评分量规和匹配规则各自版本化。

完整度至少分开显示：
1. 模块/记录/来源数量（规模）。
2. 当前已建记录的字段填充率（登记覆盖，不是穷尽率）。
3. 六维质量自评与依据（沿用既有量规，不因UI或条目多自动加分）。
4. 专业审核状态与尚待补证事项。

不要求每项目达到嫦娥的资料数量；要求采用同样清晰的结构、证据与评价口径。

## 六、嫦娥现有文件的兼容对应

| 规范位置 | 现有文件 | 处理 |
|---|---|---|
| 三个阅读入口 | 档案.html三个视图 | 继续沿用 |
| 01-项目档案.md | 档案.md、主档案结构.json、阅读内容.json | 现有MD是研究正文导出，非三个视图的完整逐字导出；以HTML阅读版为样本 |
| 02-资料与解读.md | 阅读内容.json、来源卡/、档案.html资料视图 | 新规范定义的独立MD尚未单独生成 |
| 03-档案评估.md | 质量评估依据.json、质量评估.json、档案.html评估视图 | 新规范定义的独立MD尚未单独生成 |
| 数据/ | 根目录现有JSON真源及生成文件 | 本次不移动，避免破坏脚本路径与历史快照 |
| 来源/ | 来源卡/及档案数据.json来源记录 | 保留稳定S编号和核读边界 |
| 版本/ | 版本/ | 现有不可覆写快照沿用 |
| 派生应用区 | 当前本例项目图谱及割胶机器人试读 | 目前在案例根目录；后续迁移时保留重定向与固定版本引用 |

已有12维度/49正文复合字段和17实体/233原子字段继续作为深研与底层字典，八模块是人阅读的组织方式，三者不是互相替代的三套数据。

## 七、后续案例交付检查

- [ ] 项目ID、对象边界、截止日期清楚，三个文档入口齐全。
- [ ] 八模块有内容或明确缺口，不用套话补齐空白。
- [ ] 关键数字有对象/单位/工况/来源；专利和论文统计口径分开。
- [ ] 每篇解读可回到资料，阅读范围、事实与解释分清。
- [ ] 模块统计可复算，评分有理由，审核状态真实。
- [ ] 补充清单有具体问题、验收依据、负责人及状态；未指派保持未指派。
- [ ] 新建/修订有记录，旧快照可核验；附件可见性独立管理。
- [ ] 网页三个入口布局一致，手机、键盘、深链及打印可用（接入后验收）。

模板：[项目文档标准模板-v1](../模板/项目文档标准模板-v1/README.md)。本规范优先用于文件与阅读结构；领域专业字段按既有标准补充，不扩大为另一套数据库字段。
